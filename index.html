OpenShell from the inside

How NVIDIA OpenShell 0.1.2 contains an AI agent · Docker driver on WSL 2 · every claim tied to evidence

An AI agent that can run commands can also be talked into running the wrong ones. OpenShell is NVIDIA's open-source runtime for putting such an agent in a box: it decides which files the agent can touch and which network connections it can open. This page shows how that box is built. Hover, tap or tab to any part to see what it does and how we know. Switch to Learn for a guided lesson.

control plane (stores and delivers rules) supervisor (decides, holds secrets) workload (contained, untrusted) kernel (enforces)

Figure 1

System map: what runs, and where

The thing that decides (the supervisor) and the thing that is contained (the workload) are two separate containers. The workload has no network at all; everything it does to the outside world passes through one channel.

Figure 2

Where your policy goes

One YAML file is split in two. The file rules are fixed at startup and enforced by the kernel inside the workload. The network rules can change while the sandbox runs and are evaluated by the supervisor outside it.

Figure 3

The locks, and the one kernel they stand on

The locks are independent checks on different things, not shells nested inside each other. Each stops something the others do not. All of them rest on a single Linux kernel.

Figure 4

The life of a connect() call

The agent's connect() is paused by the kernel and handed to a decision-maker outside the workload. The answer is either a clean EACCES or a connection that the supervisor opens on the agent's behalf.

Figure 5

Lifecycle and trust

No untrusted code runs until the box has proved it is closed. If the supervisor disappears, the workload is frozen first and killed if the supervisor does not come back.

Limits

What it does not protect you from

A sandbox bounds the damage an agent can do. It does not decide whether what the agent does inside those bounds is a good idea.
